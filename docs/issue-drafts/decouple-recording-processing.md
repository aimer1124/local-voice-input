# 架构：录音与处理解耦（处理队列），根治「正在处理上次录音」阻塞

> issue 草稿 — 审阅后用 `gh issue create --title "..." --body-file <本文件>` 发布，发布后可删除本文件。

## 背景

v1.7.1 → v1.8.5 的八个连续修复（僵尸回收、curl 超时、提前释放锁、预热、强杀升级、去抖）全部围绕同一个核心痛点：**录音与转写/LLM/粘贴共用一把 /tmp/vinput.lock.d 锁**。上一轮处理期间按快捷键会被拒（「⏳ 正在处理上次录音」）。现有补丁只是压平尖峰，未解耦。

同类开源项目（go-whisper、whisper-local 等）普遍采用录音与处理分离的架构，支持背靠背连续录音。

## 方案草案

- `rec` 停止后**立即释放录音锁**，音频文件 + 模式参数写入 spool 目录（如 `~/.cache/vinput/queue/`）；
- 独立的 detached worker 持**处理锁**串行消费队列，保证多段录音的粘贴顺序；
- HUD 状态归属需重新设计（「转写中」属于哪一轮）。

## 收益 / 风险

- ✅ 背靠背连续录音不再被拒；「⏳ 正在处理上次录音」提示消失。
- ⚠️ 粘贴目标窗口可能在处理期间被切走（现在也存在，但窗口期变长）。

## 数据先行

主分支已带锁/阶段计时日志（`VINPUT_LOCK_LOG`，写入 `~/.cache/vinput/lock.log`）。建议先收集 1–2 周真实持锁时长分布，确认「busy-processing 拒绝」的实际频率与时长后再决定投入。
